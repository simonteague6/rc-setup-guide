Your First Pull Request

Got your tools installed through the club's Setup Guide? This page walks you to your own text file merged into the team's rc-first-pr-practice repo. No experience needed. Do one step at a time and check it off. Your progress is saved in this browser, so you can close the tab and come back later.

STAGE 1

Get ready

This page assumes you've already worked through the club's Setup Guide, so git and the VS Code editor are installed, and on Windows, WSL with Ubuntu is set up and ready. You won't need to install anything new here.

This stage just gets your identity ready for GitHub.

Create a GitHub account

GitHub is the website where the club stores its code. Go to github.com/signup and make a free account.

  • Use an email you'll still have after graduation (a personal one, not just your UTSA email; you can add both later).
  • Pick a username you'd be OK putting on a resume. You'll be typing it a lot.

Then scroll up and type your username, name, and email into the boxes at the top of this page.

Your tools are already set up

The club’s Setup Guide already installed git, the VS Code editor, and (on Windows) WSL with Ubuntu — nothing to reinstall here.

When the rest of this page says “in your terminal”, just open Terminal (press Cmd+Space, type Terminal). open VS Code connected to WSL: Ubuntu and press Ctrl+`.

Tell git who you are

Every change you save with git gets stamped with a name and email. Set them once and git remembers forever. Run these in your terminal (in VS Code connected to WSL: Ubuntu):

git config --global user.name "YOUR NAME"
git config --global user.email "you@example.com"

Use the same email as your GitHub account. If you filled in the boxes at the top of this page, these commands already have your info in them.

STAGE 2

Set up your GitHub SSH key

An SSH key lets your computer prove it's you to GitHub without you typing a password. You make a key pair: one private half that stays on your laptop, and one public half you give to GitHub.

Make your key

In your terminal (inside Ubuntu), run:

ssh-keygen -t ed25519 -C "you@example.com"

It asks three questions. Press Enter for all three to accept the default file location and skip a passphrase (fine for a laptop only you use). You'll see a box of random characters called "randomart"; that means it worked.

Copy the public half of your key

This command puts your public key on the clipboard (safe to share; the private half stays in place):

pbcopy < ~/.ssh/id_ed25519.pub
cat ~/.ssh/id_ed25519.pub | clip.exe

If clip.exe complains, just run cat ~/.ssh/id_ed25519.pub, then select the whole output line with your mouse and copy it.

Nothing appears to happen when you run it, and that's normal. The key is on your clipboard now.

Give the public key to GitHub
  1. Open github.com/settings/keys (sign in if asked).
  2. Click New SSH key.
  3. Title: anything, like my laptop. Key type: leave as Authentication Key.
  4. Click in the Key box and paste (Cmd+VCtrl+V). It should start with ssh-ed25519.
  5. Click Add SSH key.
Test it 
ssh -T git@github.com

The first time, it asks if you're sure you want to connect; type yes and press Enter. Then you should see:

Hi your-username! You've successfully authenticated, but GitHub
does not provide shell access.
✅
"does not provide shell access" is not an error That whole message means it worked. If you instead see Permission denied (publickey), open the troubleshooting section at the bottom of this page.
STAGE 3

Get the team repo onto your laptop

Cloning downloads the practice repo and its history. Each member adds one text file in names/.

Accept your repo invite

Send Simon your GitHub username. He'll invite you as a collaborator on the practice repo. Accept the invite in your email or at GitHub notifications before pushing in Stage 7. You can clone the repo while you wait.

Clone the repo

In your terminal (in VS Code connected to WSL: Ubuntu), run these one at a time:

mkdir -p ~/projects
cd ~/projects && git clone git@github.com:simonteague6/rc-first-pr-practice.git

The first command makes a projects folder in your home directory (it's fine if it already exists). The second downloads the repo into it.

⚠️
Windows: always clone in the terminal Keep the repo in Ubuntu, not under /mnt/c/. Check for WSL: Ubuntu in VS Code before cloning.
Open the project in VS Code 
cd ~/projects/rc-first-pr-practice && code .

You should see README.md and the names folder in the Explorer.

If code isn't found, check that VS Code is installed on Windows with Add to PATH enabled, and that the WSL extension is installed.

If code isn't found, use the Command Palette in VS Code to run Shell Command: Install 'code' command in PATH, then open a new terminal.

🔍 Curious? See the repo's history

This repo starts small. Run this to see its commits as members add files:

git log --oneline --graph --all

Your commit will appear here after it is merged.

STAGE 4

Make your own branch

main is the team's shared copy, so you never work on it directly. A branch is your own workspace: nothing touches main until the team approves your pull request.

Check where you are

From now on, run everything in VS Code's built-in terminal (Ctrl+`); it's already inside the project folder.

git status

You want to see On branch main and nothing to commit, working tree clean. That means you're starting from a clean copy of the team's code.

Create your branch

Two things are happening: create the branch, then move onto it. The one-command version does both:

git switch -c feature/add-your-username-name

Under the hood, that's the same as these two commands run one after another:

git branch feature/add-your-username-name
git switch feature/add-your-username-name

git branch creates the branch; git switch moves you onto it. switch -c is the shortcut for both. The feature/ prefix makes the branch easy to spot. VS Code shows your branch in the bottom-left status bar.

STAGE 5

Add your text file

Your first contribution is one text file in names/. The point is to practice branching, committing, and opening a PR.

Create your text file

In the VS Code Explorer, right-click the names folder, choose New File, and name it your-username.txt. Use your GitHub username so it won't collide with someone else's file.

Type a sentence about yourself, or anything you like, then save with Cmd+SCtrl+S. The words aren't being graded; you're practicing the Git workflow.

STAGE 6

Commit your work

A commit is a saved snapshot with a message, like a checkpoint in a game. Git isn't tracking your new file yet. Committing is two moves: stage the file, then commit it.

See what git sees 
git status

Your file shows up in red under "Untracked files." Red just means git isn't tracking it yet; nothing is wrong.

Stage your file 
git add names/your-username.txt

Run git status again if you want to check; the file turns green, meaning it's staged and ready to commit.

Commit it 
git commit -m "feat: add your-username's text file"

The -m part is the message, a short note about what this snapshot contains. The feat: prefix tells readers this commit adds something.

STAGE 7

Push your branch to GitHub

Your commit exists only on your laptop. Pushing uploads your branch to GitHub so the team can see it.

Push 
git push -u origin feature/add-your-username-name

origin is git's name for the GitHub copy of the repo, and -u links your local branch to it (you only need -u this first time).

In the output, GitHub prints a "Create a pull request" link; that's your cue for the next stage. If the push is rejected instead, see the troubleshooting section at the bottom.

STAGE 8

Open your pull request

A pull request (PR) is how you ask the team to pull your branch into main. Someone reviews your change, may ask for tweaks, then merges it.

Start the pull request

Go to github.com/simonteague6/rc-first-pr-practice. There's a yellow banner with your branch name and a "Compare & pull request" button; click it.

No banner? Click the Pull requests tab → New pull request. Set base to main and compare to your branch, then Create pull request.

Write the title and description

Title: Add YOUR NAME's text file

Description: a sentence or two is plenty. What you added, and anything you're unsure about. For example: "Adds my text file in names/. Let me know if I got the file location right."

Click "Create pull request"

That's it; your work is up for review. Simon gets a notification automatically. If nothing happens in a day or two, it's fine to ping him: "Hey, my PR is up, can you take a look?"

STAGE 9

Respond to review

A reviewer reads your change and either approves it or leaves comments. Getting change requests is normal; it means someone read your work carefully.

Read the feedback

GitHub emails you when someone comments. On your PR page, the Files changed tab shows comments pinned to specific lines. If a comment is unclear, reply and ask; that's what the thread is for.

If the review is just an approval with no changes requested, check this off and skip to the last step. 🎉

Make the requested changes

Back in VS Code, on the same branch (check the bottom-left status bar; no new branch needed), edit your file, save, then:

git add names/your-username.txt
git commit -m "fix: address review feedback"
git push

No -u or branch name this time; git remembers from Stage 7. The PR updates the moment you push.

After the merge: sync up

When your PR is merged, GitHub shows a purple Merged badge. Your file is now part of the team's main. Bring your laptop's copy up to date:

git switch main && git pull

Your branch did its job and can be deleted (this only removes the local copy; the history is safe in main):

git branch -d feature/add-your-username-name

That's the full loop: branch, build, commit, push, PR, review, merge. You've just done what professional teams do on every feature.

HELP

When things go wrong

These are all common errors. Find yours, follow the fix, and if you're still stuck after 20 minutes, ask in the club chat or grab Simon at a meeting.

🔑 "Permission denied (publickey)" when testing SSH, cloning, or pushing

GitHub doesn't recognize your key. Check these in order:

  1. Are you inside Ubuntu? If your prompt mentions PS C:\, you're in PowerShell; type wsl first. Your key lives in Ubuntu, not Windows.
  2. Did the key actually get added? Open github.com/settings/keys. If the list is empty, redo Stage 2 steps 2 and 3. A common miss: copying but never clicking Add SSH key.
  3. Did you paste the whole key? It must start with ssh-ed25519 and end with your email. Re-copy it: 
    cat ~/.ssh/id_ed25519.pub
    Delete the old key on GitHub and add this one again.
  4. Cloned with the wrong URL? Run git remote -v inside the project. If it shows https://github.com/..., switch it to SSH: 
    git remote set-url origin git@github.com:simonteague6/rc-first-pr-practice.git

Then test again with ssh -T git@github.com.

😬 "I committed to main by accident"

Very fixable, and nothing is lost. You made your commit on main instead of a branch. This recipe moves your work to a proper branch and puts main back the way it was. Run the four commands one at a time:

git switch -c feature/add-your-username-name

Creates your branch right where you are; your commit comes with it. Your work is now safe.

git switch main
git reset --hard origin/main

Rewinds your local main to match GitHub's, as if the accident never happened. (Careful: this discards any uncommitted edits on main, so commit anything you care about first.)

git switch feature/add-your-username-name

Back on your branch, with your commit intact. Continue from Stage 7.

⚔️ Merge conflict: "CONFLICT" or GitHub says the branch can't be merged

A conflict means you and someone else changed the same lines of the same file, and git needs a human to decide. It's rare here, since everyone adds their own file in names/, but if it happens:

  1. On your branch, pull in the latest main: 
    git fetch origin && git merge origin/main
  2. Git tells you which files conflict. Open them in VS Code; you'll see markers like this: 
    <<<<<<< HEAD
your version of the line
=======
their version of the line
>>>>>>> origin/main
  3. Edit the file so it reads how it should: keep yours, keep theirs, or blend them. Then delete the <<<<<<<, =======, and >>>>>>> lines. VS Code highlights conflicts and offers buttons to accept either change.
  4. Then seal it and push: 
    git add . && git commit -m "fix: resolve merge conflict" && git push
🚫 Push rejected

Read the error message; it's one of two situations:

"Permission to simonteague6/rc-first-pr-practice.git denied" or a 403 error → you're not a collaborator on the repo yet. Check github.com/notifications and your email for the invite (Stage 3, step 1), accept it, and push again. No invite anywhere? Send Simon your GitHub username.

"[rejected] ... failed to push some refs" with a hint about "fetch first" → GitHub has commits on your branch that your laptop doesn't (this can happen if you edited a file on the GitHub website, or pushed from another machine). Download them, then push again:

git pull --no-rebase && git push

If the pull triggers a conflict, the merge-conflict entry above takes over. If nothing works, screenshot the output and ask; this one's worth a second pair of eyes.

🐧 Commands say "not recognized" or nothing from this page works Windows

Open VS Code connected to WSL: Ubuntu (check the bottom-left status bar), then open its terminal with Ctrl+`. The commands on this page run inside Ubuntu.

🔍 "code: command not found" macOS

In VS Code, open the Command Palette with Cmd+Shift+P, search for Shell Command: Install 'code' command in PATH, then open a new terminal and try code . again.
